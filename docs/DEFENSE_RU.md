# Что объяснять на защите трёх этапов

Программа анализирует связи между Python-пакетами. Сам пакет не устанавливает.
В обычном режиме читает JSON API, в тестовом — локальный файл с буквами.

1. Этап 1: argparse получает параметры и проверяет их. Значения печатаются
   как ключ-значение. Неверный ввод даёт понятную ошибку.
2. Этап 2: urllib скачивает JSON, requires_dist содержит прямые зависимости.
   Условие после `;` — marker, например зависимость только для Windows.
3. Этап 3: собственный рекурсивный DFS раскрывает транзитивные связи,
   соблюдает глубину, обнаруживает циклы и подписывает версии.

A@1.0.0 → B@2.0.0 означает, что пакет A версии 1.0.0 зависит от пакета B,
чьи прочитанные метаданные имеют версию 2.0.0. В тесте эти числа заданы
в JSON, в реальном репозитории получены из info.version.

Версия `2.0.0` и ограничение `>=2` различаются: первая — конкретный
релиз метаданных, второе — условие допустимости версии. Программа показывает
конкретные версии, но не заменяет resolver pip.

На ромбе A требует B и C, оба требуют D. DFS идёт A → B → D,
возвращается к A и проходит C → D. В графе D одна, а связей к ней две.

Цикл ищется по текущему пути path: A → B → C → A. Когда A снова
встречается в текущем пути, цикл записывается и ветка останавливается.

Один visited недостаточен при ограничении глубины: пакет можно сначала
найти по длинному пути на границе, а затем по короткому. Поэтому
expanded_depth позволяет раскрыть его ещё раз с большим остатком глубины.

Глубина 0 показывает корень с версией. Глубина 1 — ещё и прямые зависимости.
Версии граничных вершин читаются, но их дети не раскрываются.
Граница анализа и подтверждённый лист — разные случаи.

Цикломатическая сложность считает точки ветвления. Лимит — 10 на блок.
Radon учитывает также and/or и проверяет вложенные функции.
Большие проверки разделены на отдельные понятные функции с одной задачей.
Полный результат находится в docs/complexity.json.
